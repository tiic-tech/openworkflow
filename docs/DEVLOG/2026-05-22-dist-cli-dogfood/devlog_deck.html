OpenWorkflow dogfood note

我差点用错了当前能力入口

这个 deck 只讲一个小切口：在 OpenWorkflow 自己的仓库里，Agent 应该从 repo dist CLI 读取最新能力，而不是相信全局安装的旧 binary。

Use arrow keys or the navigation buttons.

Scene

同一个命令名，两个能力世界

openworkflow --help 看起来是正确入口。但在 dogfood 开发仓库里，命令名不等于版本来源。全局 binary 和 repo-built dist CLI 可以给出完全不同的 command boundary。

Global binary

  • init
  • validate
  • sync
  • doctor
  • clean

Repo dist CLI

  • handoff / inspect / context
  • draft / register / check
  • summaries / summarize
  • git-automation
  • JSON report envelope

Evidence board

四个证据把问题钉住

AGENTS.md 要求先跑 OpenWorkflow help，并用 handoff 作为严格信任门。
Global help 只暴露旧的 maintenance command surface。
package.json bin.openworkflow 指向 dist/cli/src/index.js。
index.ts 源码 dispatch 了 handoff、context、inspect、git-automation 等新能力。

Terminal replay

Agent upgrade

把一次小偏差变成操作规则

OpenWorkflow 的 dogfood 模式需要先确认能力入口，再加载上下文。否则 Agent 可能在第一步就相信了过期的 command boundary。

  1. 在 OW 自举仓库里，用 node dist/cli/src/index.js --help 确认最新能力。
  2. 用 node dist/cli/src/index.js handoff --root . --json 作为 trust gate。
  3. 用 context --handoff --json 获取 bounded startup packet。
  4. 不要手改 managed surface；产品修复回到模板、registry、schema 或源码。

Takeaway

能力发现入口也是产品契约

Agent 的上下文入口如果不受控，后面的所有推理都可能建立在过期能力上。

这就是 dogfood 的价值：系统最有用的契约，往往是在自己差点被误用的时候显形。
